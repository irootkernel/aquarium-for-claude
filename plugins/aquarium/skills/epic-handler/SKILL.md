# Epic Handler

> **Claude Code delegation:** when this skill, or a reference or Procedure node it follows, hands a step to another Aquarium skill — however it phrases the hand-off, and whether it writes `/aquarium:<name>` or names the skill bare — read that skill's `SKILL.md` in full from this plugin (`../<name>/SKILL.md` from this skill's directory) and follow it as the delegated step instead of calling the Skill tool. Claude Code reserves most Aquarium skills for the user to type: it refuses the Skill tool for them and, once it has refused, forbids carrying out their workflow any other way. When you hand such a step to a subagent, put that file's absolute path in its assignment and have it read the file, because a subagent cannot load a gated skill through the Skill tool. Running another skill's bundled script is not a hand-off. A continuation request, routed repair, offer, or recommendation that the text has you return or report to the user is not a delegation: name its slash command, do not run it yourself, and stop where the text stops.

Read [commit-attribution.md](../../references/commit-attribution.md) for message formatting and change origins, within this skill's existing effect boundaries.

Read [review-result-handoff.md](../../references/review-result-handoff.md) for producer/consumer checks and same-operation result recovery. Read [review-routing-contract.md](../../references/review-routing-contract.md) for route selection, route-specific readiness, evidence combinations, recovery, and assessment ordinals. Read [review-intent-contract.md](../../references/review-intent-contract.md) for the shared Review Brief and criterion-level completion assessment. Read [mulgae-review-contract.md](../../references/mulgae-review-contract.md) only when the selected review route is `mulgae`.

Deliver one roadmap epic as a sequence of goal-centered task executions. Own its outcome, order, evidence, and commit boundaries. Select `execute` by default, `plan-only` for a non-mutating plan, `plan-handoff` only when another agent will continue, and `resume` for continuation. Treat "plan only" as `plan-only`; for `plan-handoff` or its resume, read [plan-handoff.md](../../references/plan-handoff.md) and follow it.

Do not invoke `/aquarium:task-handler` or its phase skills; they separately strengthen the procedure around one user-guided task goal. Always read [evidence-residency.md](../../references/evidence-residency.md), [finding-disposition.md](../../references/finding-disposition.md), [release-notes.md](../../references/release-notes.md), [documentation-governance.md](../../references/documentation-governance.md), and [epic-execution-sot.md](../../references/epic-execution-sot.md). On the Podway path also read [procedure-node-contracts.md](../../references/procedure-node-contracts.md).

Use Podway by default. Exclude it only when the current user explicitly opts this epic out before its first managed session starts or a higher-priority instruction prohibits it. For an opted-out epic, do not inspect Podway, load `/use-podway`, or read [podway-integration.md](../../references/podway-integration.md), and do not carry the opt-out into a later workflow.

Otherwise read the Podway contract, then use one adequately selected Goal-family session per member-task, pre-validation remediation, or closeout goal and one adequately selected Validation-family session for the final epic audit and its audit-scoped remediation. In `plan-only`, create neither goal nor session; in `plan-handoff`, create the first Podway session only after approval, attach the plan, and stop before work. Podway strengthens local execution memory but does not prescribe a phase workflow or replace the roadmap DAG.

Goals below describe workflow objectives. Work under a Claude Code session goal only when the user has set one, whether Podway is active or opted out. Plan approval and a Podway goal do not authorize a Claude Code session goal. Continue an existing authorized Claude Code session goal within its own scope and lifecycle; otherwise proceed without one.

## Establish and Approve the Epic

Require one mutable Git repository, one canonical roadmap path inside that repository, and exactly one epic ID present in that roadmap. Reject task-only requests, multiple epics, requests without one canonical roadmap epic identity, and external roadmap authorities. Inspect another repository read-only only when the roadmap explicitly names it; never mutate or create a goal for it.

Before requesting approval:

1. Read repository instructions, the epic, every member task, `docs/README.md`, roadmap and canonical-document links, relevant role owners, required artifacts, explicit dependencies, and any linked active dossier. Resolve the requirement-bearing canonical document set without asking the user for paths. Use the dossier when one exists. When no dossier is declared and a waiver path remains eligible, assemble the shared composite execution SOT and disclose its source paths and requirement owners in the plan. A declared dossier whose link cannot be resolved is a semantic gap, not dossier absence. Apply the shared dossier routing before Epic plan approval or managed session creation. On an eligible `execute` entry, continue with `/aquarium:new-feature` in this conversation under the shared contract; do not ask for another skill invocation. Other work-definition routes and non-executing modes report the exact continuation. Never switch a running Epic session in place.
2. Inspect branch, upstream, HEAD, staged, unstaged, untracked, and conflicted state. Separate epic-owned work from existing work and record the starting revision.
3. Discover repository-native verification, Gaori, `/use-gaori`, documentation synchronization, Sanho, `/use-sanho`, lifecycle, commit guidance, and only the prerequisites of each selected review route. Use [review strategies](../../references/review-strategy-contract.md) to recommend `mulgae`, `subagent-review` or `herdr` from the goal, scope, difficulty, impact and uncertainty; record the user-selected route in the existing envelope, preserving any explicit choice or waiver for member and whole-Epic checkpoints. Record the exact target, reviewer or waiver authority, and assurance limit. Treat each CLI, repository configuration, project MCP, and agent skill as independent state; a selected-route prerequisite gap never starts another route automatically.
4. Build a dependency DAG. Distinguish member-task edges from pre-epic local or explicit external prerequisites. For every prerequisite record repository, canonical ID, exact revision, lifecycle state, dirty state, evidence, and owner. An incomplete member-task predecessor determines execution order and does not block initial approval. A pre-epic or external prerequisite is satisfied only by committed work at the required revision with verified evidence; if unmet, stop before goal creation or mutation and report the owner and required sequence.
5. Order tasks by dependencies and then roadmap order. Split a cycle only when authority defines pre-validation and finalization; otherwise stop and report its nodes, owners, and missing authority.
6. Preserve successfully terminal tasks, start at the earliest non-terminal task, and retain every task for the final audit. Stop rather than replace a different active goal. The shared explicitly consented missing-topology transition applies only to this Epic's own running session.
7. Honor an explicit pre-session opt-out without Podway discovery. Otherwise apply the shared contract's readiness and session checks. On degraded readiness, route a missing or unsupported global Podway CLI or `use-podway` skill to `/aquarium:dev-setup-global`; route repository configuration or managed-Procedure gaps to `/aquarium:dev-setup`; then stop and ask the user to choose the exact routed repair or an explicit opt-out for this epic.
   - A matching recoverable Aquarium session becomes part of the plan. Only when starting a different session, present the existing session and obtain the shared contract's explicit preserve, lifecycle, delete, or eligible-replace choice. Never route by skill owner or describe the choice as setup repair.
   - A disposed terminal session with verified handoff evidence and a current `session.start_replace` template becomes an exact successor candidate. Include its automatic archival in the epic envelope and, after approval, execute the template's current plain `start` argv without a separate reset before re-observing and beginning the prepared epic session.

Produce one concise, decision-complete epic plan: goal and non-goals, dependency DAG, task order, requirement owners and resolved execution SOT source paths, expected outcomes and commit boundaries, per-task documentation promotion, checks, review targets, lifecycle changes, external handoffs, the active dossier and its repository-defined closeout or the dossier's explicit absence, and known gaps. Avoid unnecessary phase or file mechanics. Preserve the selected mode in every continuation.

Ask once for explicit approval of the plan and execution envelope. When no dossier is declared, require that approval to waive the dossier explicitly; generic approval is insufficient. When the work meets a creation threshold, this is the second confirmation after the user chose to consider a waiver. Disclose the following effects separately within that one approval: bounded implementation and checks; selected review routes and source transmission; delegated acceptance of exact member-Task and owned correction candidates, including lifecycle, record, and release-note decisions, and internal whole-Epic validation results; eligible evidence promotion; scoped staging and exact restaging; one normal completion commit per planned member Task; one commit per verified owned correction group within the existing remediation budget, including reopened Tasks, pre-validation corrections, and Epic seams; and final closeout preparation with one closeout commit after the user's final Epic acceptance. Include any required dossier deletion. These are distinct grants within the same envelope; a normal member-Task grant alone never authorizes correction or closeout commits. Exclude checkpoint or other extra commits, automatic route changes or waivers, amend, push, PR or release changes, rollout, installation, another repository, unrelated work, and undisclosed destructive actions. A commit never authorizes upstream publication.

By default the envelope must cover creating or resuming each prepared managed session, the separate fenced `begin`, bounded evidence and decisions, goal revision and rework, terminal completion, supported disposition, and eligible replacement after the authoritative roadmap, commit, review, and worktree evidence is re-read.

`plan-only` stops without mutation. `plan-handoff` also discloses the private temporary plan file, artifact attachment and propagation, running-session stop, exact resume report, and final cleanup. Approval that explicitly omits Podway covers the same envelope without those operations and therefore without plan handoff.

Accept an opt-out only before the first managed-session mutation. Afterward classify every stop or opt-out request through the shared `Handle In-Progress Stop Requests` flow; never assume pause, cancel, reset, or an in-place switch to non-Podway execution. Never mutate a conflicting session automatically.

Do not create a goal, edit files, invoke providers, stage, commit, or alter external state before approval. After approval, `plan-handoff` may perform only its disclosed handoff mutations and must stop before work. Request renewed envelope approval only when the execution SOT source set, requirements, task membership or order, repository scope, product behavior, destructive impact, external actions, or safe diff isolation materially departs from the envelope. Renew the dossier waiver when the revised source set still has no dossier. Within the current envelope, accept Task and correction candidates under the user's delegation and continue through commits and internal Epic validation without a user-review pause. Progress reports do not request acceptance. Reserve the routine user outcome decision for the final Epic closeout.

When a selected check uses Gaori, read [gaori-integration.md](../../references/gaori-integration.md). Require the agent performing the check to load and follow the installed `/use-gaori` skill before transport selection or execution, then consume the exact command result and evidence through that contract, including prerequisite routing and optional direct-command fallback.

Before each review, bind the effective route to the approved envelope or an explicit later route-change authority. Preserve the prior completed ordinal, assessment kind, finding lineage and dispositions, remaining review authority, and corrected target. Establish one Review Brief containing the named Task, Epic, or remediation goal; actual requirement set and authorities; base revision; exact target; ordered work or correction commits when present; included and excluded paths and artifacts; verification provenance; goal revision; assessment ordinal; assessment kind; mode; and approved scope. Use the same brief for route preflight and execution. Dispatch exactly one selected route: Mulgae through an executing agent that has loaded and follows the installed same-release `/use-mulgae`, Herdr through `/aquarium:herdr-review` with an explicit reviewer and isolated supported target, Subagent Review through `/aquarium:subagent-review` with three fresh base reviewers plus one UI/UX specialist when applicable, or waiver through a coordinator assessment of the complete brief. A waiver launches no reviewer and removes neither verification nor the final direct Epic audit.

A completed delegated review or waiver assessment consumes exactly the next ordinal even when it reports findings or a failing Mulgae backend check. An incomplete or failed operation consumes none; native recovery inside the same operation reuses the pending ordinal. Switching after completion uses the next ordinal, while switching after an incomplete operation retains the pending ordinal. Bind the caller-supplied ordinal continuity check to the goal revision, prior and current ordinals, selected mode, and authority. Bind the route check to the immediately preceding route and operation, effective route, requested direction, lifecycle settlement, findings, ordinal, goal revision, and remaining authority; `resume-current` fails when the effective provider differs from the preceding unsettled provider. Preserve route-specific evidence and never fabricate a run, publication, findings query, capture, or native digest. On failure, stop for explicit `resume-current`, `new-review-current-route`, `switch-route`, `waive`, or `stop`; active or uncertain native work must first reach a safe state through its owner, and no route changes automatically.

## Accept Candidates Under the Epic Envelope

Delegated acceptance is the coordinator's evidence-backed decision under the approved envelope. It is never a claim that the user inspected or accepted the resulting bytes. Record `acceptance-source=epic-delegation`, the recoverable envelope reference, the applicable member or correction grant or internal-validation authority, and the exact accepted candidate. The candidate includes the isolated diff, lifecycle and record decisions, release-note target and exact entry or non-entry decision, verification and review basis, and remaining handoffs. Recheck that composition immediately before `task-commit`; a changed candidate invalidates acceptance and affected evidence. Reassess and record a fresh acceptance within the same grant rather than asking the user about routine rework. A consumed grant cannot authorize a second commit.

Use `acceptance-source=user` only for an actual user decision. Final Epic closeout and stopped-outcome acceptance require it. At final closeout, present the completed Task and remediation commits, exact validated baseline, checks and any user-owned functional verification, remaining handoffs, and the prepared lifecycle, dossier, record, and release-note diff. Keep the Epic in its pre-success state in the authoritative committed roadmap until that acceptance. Do not claim user verification that has not occurred.

If the user requests changes, route them to their canonical owner before committing closeout. Closeout-only changes rework the current closeout Goal and its focused checks. A change to validated implementation first requires settling the current session through its authorized native lifecycle, then returning to owned correction and validation; never nest sessions or use the `validated-closeout` substitute as coverage of changed implementation. Reuse the envelope only for covered work and unconsumed correction authority; obtain new authority for a material departure or exhausted review budget. Invalidate affected validation evidence, repeat the required audit and review, and present the new exact candidate for final acceptance. Preserve review ordinals and findings across sessions and never reset them merely because final acceptance requested rework.

   Maintain changed behavior in its canonical owner, then affected guide links

Otherwise preserve the complete correction set requiring provider assessment; its correction receives one ordinal-four `remediation-confirmation` restricted to the source finding IDs, correction commits or exact source delta, invalidated criteria, directly affected callers, contracts and tests, and correction-caused regressions. Carry unaffected criterion assessments only when current evidence proves they remain valid. ## Audit and Remediate the Epic

After all tasks are terminal, the Coordinator or an authorized Executor executes due repository checks and supplies actual results for the latest committed Epic state. The report-only Evaluator audits its original requirements and current artifacts without source mutation or check execution; the Coordinator records the aggregate audit and check result. Build a requirement-to-owner-to-production-to-test-to-document matrix across every task and inspect integration seams, consumers, persistence, concurrency, migrations, generated artifacts, recovery, operations, and roadmap consistency.

Include applicable guides and their original canonical sources in that matrix.
Check affected feature boundaries across Tasks for current behavior, links and
local instructions. Complete due canonical-document and guide corrections,
required final prose passes and affected checks before whole-Epic review under
the existing correction and evidence rules.

- Before a whole-epic review, verify every member-task `Aquarium-Evidence` manifest and payload without local runtime. Load findings only for `hardening-deferral`; retain other purposes for named consumers. Use an available exact run for legacy `Mulgae-Deferred-Run` and `Mulgae-Deferred-Finding` trailers. When that run is gone, do not promote it: record an evidence gap and cover its paths and current requirements in the current remediation-eligible whole-epic audit. Podway and trailer prose never replace evidence.
- Revalidate each deferred finding against the latest epic snapshot when its native evidence remains available.
