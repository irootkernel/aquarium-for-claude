# Adaptive workflow execution

Task, Epic Goal and Validation use the shared [adaptive selection, qualification
and recovery contract](adaptive-procedures.md). Design and Diagnosis use the same mapped consumer below. An opted-out workflow
and non-Git new-project perform no Podway discovery. Direct Task phase invocations
retain their leaf contracts.

## Select and admit the actual work

Before approval, use the ordinary assignment's `procedure_plan` and original
sources for read-only fit selection through `prepare_adaptive_procedure.py` in
`plan-only` mode. Prefer an adequate existing definition. Reconcile adopted
repository customizations before selecting an alternative; optional templates
and historical bundles impose no new policy. Disclose execution-definition
preparation and locally ignored retention in the existing execution envelope.
Do not perform product work during that preparation interval.

After approval, `prepare_adaptive_procedure.py` produces exact source, binding
and coverage targets. `qualify_adaptive_procedure.py` requests an ordinary
report-only suitability assignment for a new or changed definition. Dispatch
that assignment through the existing native harness and supply its actual
complete report. A compatible due Task plan Evaluator can cover both scopes in one
call. Adequate known reuse preserves the original first due checkpoint, including
Goal without a plan Evaluator. Prior definition evidence for unchanged adopted reuse
is not a fresh current report.

Use `manage_adaptive_procedure.py inspect|retain` with every approved `--root`,
`--entrypoint`, selected `--review-route`, exact `--source`, `--binding` and
`--qualification`. The qualification file contains the ordinary `assignment`
and actual `assessment` when due, plus `combined_task_plan` when applicable.
`retain` also needs its approved `--write-root`. The selected setup inspector
accepts the same exact inputs through `--podway-binding` and
`--podway-qualification`. Neither entrypoint starts or advances a session.
Unrelated missing templates and unselected provider readiness cannot block an
intact selected definition. Existing canonical/custom/formal diagnostics and
admitted legacy continuation remain available under their original contracts.

Current technical reviews select `subagent-review`, not the retired
`independent-review` route. Admission, suitability and current-node recovery
check the actual selected route against any explicit current-route choice,
including mapped fields. A route-neutral qualified operation keeps its existing
contract. Never reinterpret a retained old route as the new route; follow the
[retirement contract](review-routing-contract.md#retire-the-independent-review-name)
while preserving exact bundles, findings and remaining authority.

Retain a complete qualified self-contained bundle before starting. Use the
current paired Podway skill and released native start template for that retained
source and expected native digest. Re-observe, resolve the prepared session,
and only then execute its separately authorized fenced `begin`. A matching
definition does not establish matching work identity: reconcile actual roadmap
identity, current goal, plan, approval, pending effects and remaining grants.

## Consume mapped current work

After start and on every recovery boundary, run:

```bash
python3 <installed-shared>/manage_adaptive_procedure.py context \
  --repository <worktree> --root <approved-root> \
  --entrypoint <task-handler|epic-handler|epic-validator|new-feature|new-project|refactor|war-room> \
  --qualification <ordinary-context.json> --session <native-session-id> \
  --podway <supported-executable>
```

Use an available supported interpreter with YAML and `jsonschema`. An arbitrary
target repository's Python or an Aquarium development checkout is not a runtime
prerequisite. `context` resolves native ID/version/digest across all approved
roots and revalidates current fit/suitability before returning the current native
status, selected evidence, typed active items and mutation templates. It performs
no progression, provider dispatch, item recording or commit.

`prepared-resolved` permits the Coordinator's already authorized native begin after
work reconciliation. Keep the actual adopted session ID, native tuple, bundle reference and original invocation/authority in the existing local ordinary orchestration checkpoint before work. This recovery binding introduces no central state file or mandatory receipt. `dispatch-ready` supplies an ordinary v3 assignment for
its mapped Executor or Evaluator. Dispatch through the existing harness, bind the
actual returned public handle and receive the complete result. `coordinator-owned`
keeps Decisions, technical review operations, report assembly, acceptance and
Git boundaries with the Coordinator. Read full selected native evidence through its
supported pagination before work; bounded previews do not substitute for it.
For each native item, use its actual declaration, operation ID/digest and typed
recording contract. Re-observe after recording and use only currently available
native transitions. A negative assessment still completes its Action and follows
the actual negative router; it grants no effects or authority.

For Tasks, the approved ordinary `procedure_plan.phase_skills` maps placements
to due leaf skills. Load those complete installed skills when their placement is
current. The known canonical contract supplies its original phase owners; a
custom operation follows its qualified approved ownership and actual operation
instructions. A documentation delivery can own documentation and verification
without an unused implementation or refinement step. Code/test changes retain
due refinement and Deslop under original repository requirements. Determine
applicability from the actual work before constructing the candidate; graph
omission cannot waive an obligation. Affected canonical documents or applicable
directory guides make documentation work due under
[directory agent guidance](directory-agent-guidance.md), including required final
prose passes and pre-review maintenance. Apply this through the existing
phase mapping and Goal/Validation responsibilities. Goal and Validation never
inherit the Task phase sequence. Cold Validation uses a fresh independent
Evaluator; internal Validation keeps its logical Epic Evaluator when supported.

Selection and pre-start qualification validate every configured placement in the
selected family's `phase_skills`, `design_phases` or `diagnosis_phases` map,
including later work. `phase_skills` maps each actual placement to a list of
supported family leaf names, such as `quality: ["qa"]`. `design_phases` and
`diagnosis_phases` map each placement to one supported phase-name string.
They use the same leaf and application-boundary checks as
runtime dispatch. Defaults, valid grouped ownership and inert maps for other
families keep their existing behavior. Invalid applicable maps stop before
source authoring or adoption.

## Mapped handoff and recovery

For an explicitly requested plan handoff, record the approved attachment endpoint
and first-work placements in `procedure_plan.plan_handoff`:

```json
{"attachment":{"node":"approved-input","item":"plan-link"},"first_work":["write-doc"]}
```

These are approved invocation mappings into the exact qualified source and binding. They
are not reusable runtime values. Keep the initial native session UUID and current
`plan-handoff` or `resume` mode in `target.plan_handoff_runtime`. Follow [Plan Handoff](plan-handoff.md) for its session-bound path, atomic exact bytes, permissions
and retention. Attach at the mapped Action. At a mapped first-work placement with a
declared artifact selector, verify its current native selection. If the source declares
no such selector, restore the actual verified attachment metadata from the existing
ordinary checkpoint and verify its native session, source attempt and exact local bytes.
A missing declared selection never falls back to checkpoint metadata. `context` returns
`attachment-required` before an absent attachment and `stop-before-work` for the
requested handoff after verifying the complete native metadata and exact local bytes. It
returns no dispatch at either boundary.

Retain the actual verified artifact metadata in
the existing ordinary checkpoint and `target.plan_handoff_runtime.artifact`, together
with its returned native `artifact_reference`. Later Executor or Evaluator resume verifies
those same bytes even when its current native selector no longer directly carries the
original artifact. Native selected metadata remains primary at the attachment and
first-work placements. Missing retained metadata or a native source-attempt change stops
before later work; native rework remains the invalidation authority. Resume verifies the
same artifact before work. Retain the returned `artifact` and `artifact_reference` in
the existing ordinary checkpoint and restore them in `target.plan_handoff_runtime`
before later Executor or Evaluator recovery. The attachment reference binds its native session
and source attempt; current native counters must still match. Missing metadata, changed
plan bytes or an invalidated source attempt stop further work and preserve the session.
Successor sessions attach the same initial plan path and identity under the existing
handoff contract.

For internal Validation carrying the Epic handoff, map its baseline
attachment and every feasible first audit or remediation placement as a work boundary.
Validation assessment work verifies the inherited plan before dispatch; Task and Goal
keep their product-work boundaries. These session bindings stay outside reusable
definitions.

Prepared and non-bootstrap running recovery use the retained tuple, never a mutable
origin path. Missing/corrupt/ambiguous adopted bundles stop without generation or
fallback. Original admitted canonical/custom/formal sessions continue under their
supported released contract without fabricated adaptive metadata. Reconcile that
provenance from actual native and ordinary records; an unresolved adoption identity is a
proof gap, not permission to assume a legacy fallback.

On in-session re-entry, compare
the complete extracted original criterion and part set with the approved coverage basis.
Keep its original source identities, adopted status and report provenance. Changes
outside selected Markdown sections or JSON criteria, including lifecycle bookkeeping, do
not refresh the report target or force another Evaluator. A change inside that extracted
basis still requires its affected checks; lifecycle-looking text inside a criterion
receives no automatic exemption. Strict raw source pins remain due before start. Current
plan, authority, review, adopted source and exact execution-definition checks remain
due. A changed basis returns the affected in-session planning/Evaluator route; it cannot
manufacture a post-start pre-start assessment. Retrieve missing ordinary/provider
delivery from the same pending operation before a new call; keep expected reports,
original findings, route, ordinal and remaining authority. Eligible whole-set local
settlement remains within its original effect grant, including confirmation-only mode. A
review switch or waiver needs its existing explicit direction and native continuity
gates, not a new routine question.

When an approved output changes a declared original source, optional
`qualification.applied_source_recovery` keeps that original readable while the
existing session continues. It uses the `sources`, `proposal`, actual `approval`
and current ordinary `checkpoint` fields below. It does not require the pending
Executor or Evaluator's future assessment or selected report artifact. Supply this
input only after the exact approved images have been applied, including any
approved deletion; an application Executor can then finish its evidence-only
handoff, and subsequent evidence Executors, Evaluators and Coordinator Decisions keep
their actual admitted roles.

This continuation is limited to a running session. A fresh native observation and
`status --verbose` must agree on the session, revision, goal, Procedure tuple and
current placement. The current attempt must be present and valid in native trace
history, including the released `active` lifecycle. Missing or invalidated current
attempts return `not-established`. The helper rechecks native state, approved
postimages and the retained definition before returning the normal mapped result.
It never advances a node, dispatches a new pre-start assessment or claims success.
Prepared, completed and cancelled sessions cannot gain work through this input.

Dispatched assignments retain their original `work.requirement_sources` and
coverage. `target.applied_source_context` supplies readable capture/Git references,
original pins, approved current images and the existing approval objects, including
their references when present. Recipients read those pinned originals to assess the
current deliverables; the new text and generated coverage do not replace the
original authority. Other source reads, genuine plan/review/effect changes and
current suitability checks remain in force. Unchanged known reuse preserves its
first due checkpoint. This input and `finalization_recovery` are mutually exclusive.
Neither creates effect, acceptance or commit authority, and unproved chains of
source edits still stop.

A caller recovering approved finalization changes to original sources, including
last-consumer deletion, may supply optional
`qualification.finalization_recovery` in its existing context input. This is an
in-session, Coordinator-only recovery path, not preparation or permission to resume product
work. Keep the original assignment, suitability report, coverage and static basis.
The input contains:

- `sources`: original source `path` plus either an already retained worktree-local
  `capture` path or a full immutable Git `commit`. Recovered bytes must match the
  original source pin and the first approved before-image. Recover each affected source,
  including a roadmap changed alongside a deleted dossier. Do not substitute a
  promoted summary or the approved new text for original criteria.
- `proposal` and actual `approval`: the existing exact diff/targets approval shape,
  checked against current applied postimages, including the approved source absence.
  Design and Diagnosis require `source: user` in both continuation and settled
  recovery. Other families retain their applicable `source: user` or
  `source: epic-delegation` source-edit provenance. Coordinator verifies the existing
  parent grant, work, exact scope and remaining authority. Delegated source-edit
  approval establishes no user acceptance, goal achievement or additional effect
  authority; final Epic and cold Validation acceptance remain user-owned.
- For successive separately approved changes, replace `proposal` and `approval`
  with ordered `changes`, each containing its actual `proposal` and `approval`.
  Supply one representation. Each recovered original starts at its original pin.
  Every later target before-image must equal that path's preceding approved
  after-image, including absence. Each step retains its exact approval and
  applicable family authority. The helper checks the last postimage of every path,
  including paths omitted from its final step. Original criteria remain pinned to
  the original bytes. Dispatched source context retains the complete `changes`
  and a derived `targets` map of the last images; that map is not a cumulative
  approval. The existing single-change input and context remain supported.
- `assessment`: the current affected ordinary Evaluator report's existing `path` and
  `sha256`. The due affected Evaluator assignment requests `target.files`, mapping
  approved current paths to postimage SHA-256 values, and `target.deleted_before`,
  mapping approved deleted paths to their deletion before-image SHA-256 values.
  For a chain, cover every path's last approved state, including earlier-only
  paths. A final deletion after an earlier edit uses that deletion's before-image;
  the original requirement-source pin remains unchanged. Both maps accept
  bare or `sha256:`-prefixed identities. A deletion-only report may omit `files` or
  use an empty map. The due checkpoint must pass; a null or absent
  `checkpoint_result` uses `verdict`, while an explicit negative or empty checkpoint
  result cannot fall back to it. A scoped pass can retain honest global future
  gaps. Keep these maps in the existing ordinary report without a separate report
  or duplicate Evaluator cycle.
- `checkpoint`: the existing orchestration checkpoint with the current session,
  revision, goal revision and exact Procedure tuple in `checkpoint.procedure`,
  alongside its ordinary `work` identity. This public context can be the direct
  status returned by execution context or the existing mapped dispatch shape
  whose `procedure.native` contains that status. `checkpoint.native` carries the
  harness and available public agent metadata. Historical local captures that
  stored public workflow context in `native` remain supported only when
  `procedure` is absent. A declared direct or wrapped `procedure` must be current;
  a contradictory or malformed value never falls back to `checkpoint.native`.
- `selected_evidence`: the existing native evidence-read envelope selecting that
  exact report artifact from a mapped Evaluator in the current workspace. The report and
  checkpoint must identify the same work. Available ordinary session, attempt,
  source and binding metadata must agree; unavailable optional metadata needs no
  duplicate snapshot. The original consumer need not remain active after completion.

This optional path reads native `status --verbose` and compares its session, revision,
goal revision and exact tuple with the initial observation. Native current-trace entries
must establish that the selected producer and consumer attempts remain valid. An
unchanged attempt counter alone cannot establish validity after native rework. An
unavailable verbose status/history container or a non-list history entries contract
returns `unsupported-runtime`. In supported current history, an absent or invalidated
selected attempt returns `not-established`. The status and approved postimages are
rechecked after qualification; a concurrent native change returns
`reassessment-required`, and a changed postimage requires renewed approval.

All original criteria and compound parts are extracted from the pinned original bytes
and compared by the existing in-session suitability contract. Other original sources
and the exact retained definition still receive their ordinary checks. Current report,
agent, approval and native-chain provenance remain Coordinator responsibilities; declarations
and artifact identities do not authenticate execution. This path returns
`finalization-resolved` with `dispatch: null`, preserving current authority and pending
operations. It permits only Coordinator reconciliation of the already authorized pending
finalization/disposition and makes no achievement or acceptance claim. Missing evidence,
source drift, changed approved postimages or changed static basis stop recovery. Strict
pre-start pins and ordinary missing-source failure remain unchanged.

`terminal-resolved` reports native state without claiming achievement. Native
session-goal mappings, current final Evaluator and actual eligible acceptance own
success. Task acceptance stays user-owned unless its existing parent workflow
explicitly owns the delegated boundary. Goal member/correction and internal
Validation grants cannot accept final Epic or cold Validation. Final overall
Master acceptance remains separate.

After a successful commit with interrupted completion/disposition, restore the
exact accepted target and actual commit evidence, resolve the same session and
finish only the pending native terminal work. Never repeat the commit. Normal
declared rework and approved disposed-terminal successors use existing native
operations without another question. Unexpected missing topology in a running session uses the explicitly consented atomic transition below. Preserve the old snapshot while preparing and qualifying its successor.

At closeout, follow [Procedure preservation](procedure-promotion.md#closeout-callers)
for eligible definitions with established successful use and distinct future reuse value. Group offers in the
Task/Epic or final Design/Diagnosis presentation; content consent and any separate
commit grant do not alter original acceptance. Apply only after the original
workflow finalizes. Skip the helper when no eligible Procedure was used.

## Design entrypoints

`new-feature`, `new-project` and `refactor` use the same exact tuple resolver,
qualified binding and ordinary current-operation handoff. Prefer adequate unchanged
Design definitions; their grouped discovery, quality and application assessments
remain the first due checkpoints. New or changed definitions require the existing
exact pre-start suitability/bootstrap. An approved normal successor restores its
actual session identity and retained source; it inherits no prior product verdict
or approval. Missing topology preserves the current session for the existing
recovery owner. Diagnosis and shared unexpected atomic replacement follow the sections below.

The public `manage_adaptive_procedure.py` and `prepare_adaptive_procedure.py` branch before native imports, executable
discovery, source rendering or repository initialization when `--podway-opt-out`
is present for a Design entrypoint, or when `new-project` has no Git metadata.
This returns exit 0 and `podway-inapplicable`, its reason and Coordinator ownership.
No `--root`, source, binary or qualification is required by the admission CLI on this branch. The preparation CLI still reads its ordinary assignment to identify the entrypoint; it does not select or render a source. The preparation API accepts the same explicit `opt_out=True`. Git-backed subdirectories retain the native path. Continue
the original ordinary assignments, approved external drafts, independent grouped
assessments and exact document approval. An explicit opt-out is an invocation
choice, not an unavailable-tool fallback. Native invocations still require every
approved root and actual available runtime dependencies.

`procedure_plan.phase_skills` can map Design placements to the authorized upstream
`interview`, `pm`, `seed` and `qa` leaves. `procedure_plan.design_phases` can map
work-specific placements to `context`, `discovery`, `draft`, `challenge`, `quality`
or `application`. Known exact operations and their typed/namespaced derivations
preserve original ownership. A mapped application capability always remains an
application boundary. Design QA is separate from technical review. Record `authority.review.route: not-applicable` when the actual envelope has no technical-review obligation. An actually selected technical route retains the shared structural review-control, result continuity, recovery and authority checks even for unchanged Design reuse; QA cannot substitute for them. A source lacking that proof stops before adoption or prepared begin/work. Read the complete installed upstream leaf before invocation;
readiness and provider authority remain due, and PM clipboard replacement still
needs its separate authority. Do not invoke upstream outer execution or implement
product changes from a Design assignment.

Optional current QA evidence in `target.design.quality` uses `operation_outcome`,
`raw_verdict`, `draft_sha256` and complete `findings`. Each finding retains its
original `id`, local `disposition`, `basis`, and unresolved `owner` (`discovery`
or `draft`). The adapter exposes owner counts and the original rows. Adjudicable
raw `FAIL` or `REVISE` remains operation `pass`; failed or missing operation output
returns to quality recovery. Discovery findings take precedence over draft findings.
The Coordinator reconciles these facts with actual native selected evidence and chooses
the original qualified router; this helper never records a result or advances a node.
A raw verdict with zero counts requires actual dispositions for every original issue.

Before an application Executor dispatch, supply the complete displayed proposal in
`target.design.proposal`: `diff` and `targets`, mapping each relative document path
to its exact `before` and `after` SHA-256, or `null` for absence. The actual ordinary
user approval is `authority.document_approval` with `source: user`,
`decision: approved`, and the exact same complete `proposal`. These are current
invocation evidence, excluded from reusable bindings; no new report file or receipt
is required. The adapter re-reads regular target files and returns `approval-required`
or `reapproval-required` without dispatch on missing approval, changed proposal or
changed targets. Renew the original draft/challenge/quality and actual exact-diff
approval for changed content. The Executor rechecks immediately before writing.
For evidence-only recovery after application, `target.design.applied: true` checks
the approved `after` bytes and grants no new write. Actual native application checks
and the independent application/final Evaluator remain due.

All three entrypoints retain their distinct canonical artifacts and work-definition
requirements. Feature preserves the existing Epic identity and member structure
unless explicitly changed; project produces the PRD, user and maintainer indexes,
all role indexes and per-scope roadmaps with testing-foundation after executable
prerequisites; refactor retains compatibility, migration, rollback, containment
and verification owners. Design Gates apply only to an enrolled registry.
Document approval grants no commit, implementation or publication authority.
Required delivery-input commits stay with the existing exact one-commit handoff;
without that grant, preserve applied documents and pending native finalization.

Helper and disposable native checks establish their stated layers only. Actual
upstream calls, clipboard effects, installed three-entrypoint behavior and Master
functional verification remain unverified until performed under their own authority.


## Diagnosis

`war-room` activates Diagnosis through the same exact native tuple resolver and
ordinary assignment adapter. Unchanged adequate reuse keeps its original first
investigation Evaluator. New/changed definitions keep exact pre-start suitability and
bootstrap. Original canonical/custom/formal sessions retain their supported
contracts. An explicit skill-level Podway opt-out stays outside native setup or
source preparation; the public Design-only `--podway-opt-out` flag remains scoped
to Design.

`procedure_plan.diagnosis_phases` maps actual qualified placements to `baseline`,
`investigation`, `proposal`, `quality` or `documentation`. Known released operations
and typed derivations preserve those owners. Grouped or conditional investigation
structures may use explicit approved phase ownership; a mapped document-approval
capability cannot be relabeled to bypass approval. Approved `procedure_plan.phase_skills` may map due `interview` or `qa` leaves; a quality placement defaults to the
installed `qa` leaf. This selects due work without adding an executor or invoking
upstream outer workflows. Product repair, production/shared-service mutation and
publication remain excluded.

Optional `target.diagnosis.quality` carries the same actual QA operation outcome,
raw verdict, exact draft identity and complete source findings as Design.
Unresolved owners are `baseline`, `investigation` or `proposal`: baseline evidence
routes to baseline, investigation/proposal findings through investigation. Raw
`FAIL`/`REVISE` with adjudicable output remains operation `pass`. Native selectors,
independent quality assessment and the actual guarded router remain authoritative.

Optional `target.diagnosis.conclusion` keeps cause (`established`, `no-work`,
`investigate-more`, `blocked`), scope (`task`, `epic`, `incomplete`, `no-work`) and
original `evidence` references. Established cause needs `causal_mechanism_established: true` and its declared causal basis;
no-work needs `expected_behavior_established: true` and actual supporting evidence.
An unexplained/unreproduced symptom does not establish no-work or repair. Blocked
and continuing investigations remain incomplete. These declarations preserve the
ordinary evidence boundary; they do not authenticate an Evaluator or prove causation.

For diagnostic documents, `target.diagnosis.proposal` and
`authority.document_approval` use the exact displayed diff and current target
snapshots described for Design. Changed content returns through investigation,
quality and fresh actual approval. Explicit no-change uses
`{"no_change":true,"diff":"","targets":{},"reason":"<actual reason>"}` and needs
the same exact actual user approval. `target.diagnosis.applied: true` verifies the
approved postimage/no-change and returns evidence-only effects. Every applicable
Task/Epic/incomplete/no-work path keeps QA, actual approval, document/no-change
verification and final diagnosis assessment. A diagnostic deliverable is separate
from defect repair and commit authority.

## Consented atomic supersede

Ordinary input changes and investigation hypotheses use declared rework. Only
required topology absent from the running snapshot warrants unexpected replacement.
Stop new work, settle uncertain effects and reconcile relevant descendants. Prepare,
qualify, assess and retain the successor within the existing preparation grant.
Use `adaptive_supersede.prepare_transition` or launcher `transition-plan` to produce
an ordinary checkpoint and disclosure, with no native mutation. The caller supplies
the actual missing topology, reason, title, pending operations, reconciled effects
and remaining authority from existing orchestration records. This declaration is
not a new source of authority or mechanical proof of semantic necessity.

The disclosure binds old native tuple/session/revision and lifecycle, current
placement, exact successor tuple/bundle, pending work/descendants, retained
history/results, cancellation and archival, and remaining grants. Ask for actual
explicit replacement consent. The successor becomes prepared, without beginning
work or asserting goal achievement. A new session grants no extra provider ordinal,
correction budget, acceptance, commit or publication authority.

The launcher actions `transition-plan`, `transition` and `transition-recover` use
`--repository`, every approved `--root`, `--entrypoint`, `--qualification` and
`--podway`. `--transition-input` names JSON: plan input has `title`, `reason`,
`missing_topology`, `pending_operations`, `remaining_authority`,
`effects_reconciled: true` and one unique `idempotency_key`; the other actions take
the returned `checkpoint`. Qualification describes the exact retained successor,
including an actual current suitability report when due. The helper does not write
a checkpoint file: retain the original request, resolved fences and key in the
existing ordinary local checkpoint before submission.

`--consent` supplies ordinary current user evidence
`{"source":"user","decision":"approved","disclosure":<exact disclosure>}`.
The caller must obtain that actual consent; a JSON value does not prove approval.
`transition` revalidates the retained qualified target and reobserves fresh native
workspace/session/revision fences. Changed predecessor or disclosure stops before
mutation. It submits exactly one supported `start --on-existing preserve
--supersede-reason` request, never cancel/start, reset or delete. Released running
observations do not advertise this start template; preview/released command grammar
and current native observation supply its exact supported contract.

An uncertain response returns `outcome-unknown` with the retained request/key.
`transition-recover` first performs native outcome lookup and state readback. A
found result must prove inactive cancelled predecessor, superseded disposition and
exact successor lineage; the successor must still be prepared revision zero with
no goal/attempt and resolve to its retained bundle. `--replay` permits only identical
request/key/fences after a lookup miss and unchanged predecessor readback. A miss
cannot disprove a historical effect; changed state remains unresolved. Never submit
a new start to recover an uncertain result.

Successful JSON returns `superseded-prepared-resolved`, actual successor and
preserved authority/pending records, with no dispatch. The Coordinator separately
reconciles the successor's actual work and authorized begin. `replacement-consent-required`
from planning is a successful exit-0 disclosure. After a lookup miss with unchanged predecessor readback, recovery without `--replay` returns exit 0 `same-request-replay-available`, its retained `checkpoint` and no dispatch or mutation. This status does not establish a completed transition; explicit `--replay` is required to submit the original request. Failures exit 2 with their typed
status; consent absence, stale state, native conflict, missing/corrupt binding and
unknown outcome remain distinct. Ordinary approved terminal successors and native
same-operation recovery require no repeated replacement question.
