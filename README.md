# Aquarium for Claude

English · [한국어](README.ko.md)

> Software engineering with AI Fleets, not vibe coding.

Aquarium for Claude is a Claude Code plugin for engineering reliable software with AI agents. Every task has a tracked state, completion needs verified evidence, and consequential actions wait for your approval.

## Install

```bash
claude plugin marketplace add irootkernel/aquarium-for-claude
claude plugin install aquarium@aquarium-for-claude
```

Inside a session, use `/plugin marketplace add irootkernel/aquarium-for-claude` then `/plugin install aquarium@aquarium-for-claude`. Start a new session after installing or upgrading so the active session reloads the skill snapshot.

The generated plugin is committed, so installation never depends on the submodule being fetched.

### Migrating from Root Kernel

The plugin id and the command prefix both changed, so an existing installation does not upgrade in place.

```bash
claude plugin uninstall root-kernel@root-kernel-dev-claude-skills
claude plugin marketplace remove root-kernel-dev-claude-skills
claude plugin marketplace add irootkernel/aquarium-for-claude
claude plugin install aquarium@aquarium-for-claude
```

Repositories that used the Podway integration must finish or explicitly dispose of any active session before migrating, then replace the managed `root-kernel-{task,goal,validation}-v2.yaml` procedures through a separately approved `/aquarium:dev-setup` run.

The four design skills drive Ouroboros as a bounded leaf capability and need a stable release `>=0.51.1` installed — upstream dropped the upper bound in v0.1.17; `/aquarium:dev-setup-global` diagnoses and configures it behind separate approvals; the plugin itself is installed with `claude plugin`. They shape documents only and never implement.

`task-handler` loads seven phase skills in order — `task-plan`, `task-implement`, `task-refine`, `task-verify`, `task-document`, `task-review`, `task-close`. Invoke one directly only to resume that exact phase with its required task context.

The three static review skills share one contract, `references/review-contract.md`, which owns the source scopes, consent, static-review limits, and what each route guarantees, plus `references/review-intent-contract.md` for the Review Brief and the `change`-versus-`completion` purpose, `references/review-strategy-contract.md` for route recommendations and reviewer focus, `references/finding-disposition.md` for adjudication, and `references/review-result-handoff.md` for result delivery. `subagent-review` runs three fresh base reviewers — implementation correctness, requirements and integration, and tests — plus a UI/UX specialist when the work affects user interaction, each one the bundled reviewer subagent described below; it supports all six scopes, reading Git objects for `staged`, `head`, `commit`, and `range` and the live non-ignored tree for `workspace` and `dirty`, and runs upstream's target inspector and this edition's repository-state inspector around the team. `herdr-review` supervises one fresh explicitly requested main reviewer, which runs its own native subagents, in the current local Herdr session under `references/herdr-supervision.md`: it needs Herdr client and server v0.9.3 or newer, `HERDR_ENV=1`, and the separately installed upstream `herdr` skill, which Claude Code loads as `/herdr`, supports only `staged`, `head`, `commit`, and `range`, and prefers a reviewer kind outside the Coordinator's AI family, such as a Codex reviewer for a Claude Code session. `mulgae-review` builds the same Review Brief for Mulgae's own native targets and consumes the accepted role reports under `references/mulgae-review-contract.md`, while the separately installed `/use-mulgae` skill owns the native lifecycle. The Task, Epic, and cold-validation workflows select one completion-review route under `references/review-routing-contract.md` — `mulgae`, `herdr`, `subagent-review`, or an explicit `waived` — from a recommendation by work size, Mulgae for small work, Subagent Review for medium, and Herdr for large, with route-neutral evidence, a bounded number of assessments, and no automatic fallback. `orca`, `independent-review`, and `native-codex` survive only as the route identities of earlier evidence, so a checkpoint still on v0.1.17's `native-codex` route needs an authorized switch to a current route. Upstream converged on this edition's review design between v0.1.18 and v0.1.20 — Independent Review moved onto fresh host subagents and gained the `workspace` and `dirty` scopes, its single-subagent native route retired, Herdr Review replaced Orca Review and `orca-review`, and `independent-review` became `subagent-review` without an alias — so the review contracts now ship as upstream writes them, with literal rules, and the remaining divergence is the `subagent-review` override described under How generation works.

### Roadmap commit guard

The plugin ships a `PreToolUse` hook that inspects `Bash` commands and denies a direct `git commit` in a repository whose tracked roadmap carries task lifecycle state, routing it through `task-commit` instead. The hook is local, reads only the proposed command and the working directory, and fails open when it cannot parse its input. Because Claude Code merges an enabled plugin's hooks with your own, review it under `/hooks` after installing.

### Root agent guidance

`dev-setup` makes `AGENTS.md` the sole repository-managed root guidance, as upstream has since v0.1.18, and migrates the rules of an existing root `CLAUDE.md` into it before proposing that file's removal. Claude Code reads `AGENTS.md` natively from 2.1.277, and in every session from 2.1.281, but by default only when no `CLAUDE.md`, `.claude/CLAUDE.md`, or `CLAUDE.local.md` exists in the working directory or above it: a user-global `~/.claude/CLAUDE.md` does not block it, a nested `AGENTS.md` loads when Claude reads a file beneath it under the same condition, and an `@AGENTS.md` import in a `CLAUDE.md` is never read twice. `dev-setup` checks for those blocking files from the requested working directory through the Git root and its ancestors, withholds a removal that would leave another blocker in place, and does not report the guidance ready while one remains. Through v0.1.17 this edition's setup proposed a `CLAUDE.md` that loaded the guidance through an `@AGENTS.md` import; setup now proposes removing that shim when no other loading blocker remains. On a Claude Code release below 2.1.281, where some sessions cannot read `AGENTS.md` directly, decline that removal and keep the import.

### Bundled reviewer subagent

The plugin ships one subagent, `aquarium:subagent-reviewer`, from `additions/agents/`; it was `aquarium:independent-reviewer` until v0.1.20 renamed the review skill, and like the skill it has no alias. It has no upstream counterpart: upstream's Subagent Review asks the Coordinator's native harness for fresh reviewers and ships no agent definition, while a Claude Code plugin can ship one, so the two requirements that matter become configuration — a tool allowlist of `Read`, `Grep`, `Glob`, and `Bash` with no editing, writing, or agent-dispatch tool, and `model: opus` — around a review-focused system prompt derived from the skill's reviewer requirements. Bash stays in the allowlist because a reviewer must read `git diff --cached` and `git show`; beyond the tool allowlist its read-only discipline is the prompt alone, which is stated rather than hidden — Claude Code ignores `permissionMode`, `hooks`, `mcpServers`, and `initialPrompt` on plugin subagents, so the agent declares none of them and the validator rejects all four. The prompt also carries the boundary an in-session reviewer cannot inherit from its tools: a subagent runs as the same operating-system user in the same worktree, so reading a staged or committed target through Git objects rather than working-tree copies, reading a `workspace` or `dirty` target from the live non-ignored tree, and leaving excluded state unopened are rules rather than a sandbox. Its one dispatcher is `/aquarium:subagent-review`, run standalone or as a workflow's selected route, which dispatches the whole team in a single message — each member with one assigned focus and free to report an actionable issue outside it — and records a preflight failure for the route rather than substituting another subagent type when the agent is unavailable. The agent mirrors upstream's proportional review: a `change` review starts from the exact diff and the applicable authority and expands only along a plausible affected path, pre-existing issues the target does not introduce stay alone, style preferences, speculative risks, and verification gaps are non-findings, a `completion` purpose returns per-criterion assessments, previous finding responses in the Review Brief are evidence rather than binding conclusions, and `APPROVE` is an advisory conclusion the coordinator settles after the target-digest and repository-state comparisons. The single-agent mode that applied every lens for v0.1.17's `native-codex` checkpoints went with that route. The cost is that the agent's description is loaded into every session where the plugin is enabled, which is why it is worded narrowly and negatively. Opus is the baseline for every delegated role in this edition — these reviewers, the Executors and Evaluator of ordinary workflow orchestration, `release-qa`'s executors, `epic-handler`'s optional extra-perspective subagent, and the `upgrade` skill's subagents — and Fable is requested only when the user explicitly asks, because a subagent without an explicit model inherits the session's and Fable can bill usage credits, which a non-interactive run does without asking.

### Edition upgrade skill

The plugin ships one edition-owned skill, `upgrade`, from `additions/skills/`. It has no upstream counterpart because it operates this generator repository itself: it pins the submodule to a released upstream tag, resolves every sync abort through orchestrated subagents — Opus for judgment and review, Sonnet for mechanical collection, Fable only on explicit request — while the invoking conversation decides, reviews, validates, and reports its progress at every phase boundary, and publishes the reviewed tag, GitHub Release, and local installation refresh behind explicit approvals. It refuses to run outside this repository, and its `references/rederivation.md` records the override re-derivation method and the adoption traps that are invisible in the code. Like every addition it is authored in final form: the gating flag is self-declared, generation refuses a skill addition without it, and `tests/validate.rb` asserts that a sidecar-less skill is a recorded addition and gated.

### Invocation gating

Every skill except `dev-setup`, `goal-evaluator`, `herdr-review`, and `task-commit` carries `disable-model-invocation: true` — 23 of the 27 — so Claude cannot start it on its own; you invoke it with `/aquarium:<skill>`. Several of these skills stage, commit, or mutate roadmap state, and the upstream workflow requires explicit invocation. The four open skills are upstream's choices, each on a bounded trigger: `task-commit` on an approved handler's commit handoff or a direct commit the roadmap gate covers, `dev-setup` since v0.1.18 on a request to initialize, repair, or audit project configuration or agent guidance, `herdr-review` since v0.1.19 on an explicit Herdr Review request or a handler's selected Herdr checkpoint, and `goal-evaluator`, the goal judge v0.1.19 added and v0.1.20 renamed, on an Evaluator assessment a workflow assigns. `orca-review`, which upstream opened in v0.1.14 on the same bounded trigger as `task-commit`, left with Orca Review in v0.1.19. The flag is derived from each upstream skill's `agents/openai.yaml` at sync time, so it can never disagree with the Codex policy; the edition-owned `upgrade` skill has no sidecar, so it declares the flag itself and both generation and validation assert it.

The skills that take arguments also carry an `argument-hint`, which Claude Code shows after the command name in the `/` menu — `/aquarium:epic-handler <roadmap-path> <epic-id>`, for example, or `/aquarium:subagent-review <target> [task-or-epic-id] [model] [effort]`. The Codex sidecar has no counterpart, so the hints come from one table in `scripts/sync.py`, recorded in the sync manifest and asserted against every upstream skill's frontmatter; a skill that upstream drops stops the sync rather than leaving a stale hint, as v0.1.20's alias-less rename of `independent-review` did, and the edition-owned `upgrade` skill carries its hint inline because that table deliberately rejects names upstream does not ship.

This is also why the plugin is a separate artifact rather than a second manifest in the upstream repository: Codex's plugin validator rejects `disable-model-invocation` outright, while Claude Code needs it for the same guarantee.

### Skill delegation

Upstream skills hand work to each other by name — `task-handler` loads its seven phase skills, `release-handler` uses `release-qa` for scenario QA, and `dev-setup-bundle` prepares global components through `dev-setup-global` — and Codex treats such a mention as an explicit invocation. Claude Code's Skill tool does not: it refuses a `disable-model-invocation` skill unless the user typed that skill's name in the current turn, always refuses it inside a subagent, and its refusal forbids carrying out the skill's workflow by other means, so every hand-off into a skill gated above was refused and the workflow stopped there. Generation therefore opens every gated skill derived from upstream, overrides included, with one delegation note directly under its title. When the skill, or a reference or Procedure node it follows, hands a step to another Aquarium skill — however it phrases the hand-off, and whether it writes `/aquarium:<name>` or names the skill bare — the note has Claude read that skill's `SKILL.md` in full from the plugin and follow it as the delegated step instead of calling the Skill tool, and give any subagent it hands the step that file's absolute path to read itself. A continuation request, routed repair, offer, or recommendation the text returns to the user is not a delegation: Claude names its slash command, does not run it, and stops where the text stops — the outcome the refusal used to produce. The gate is unchanged by design: a gated skill runs only because the user started it or a user-started skill handed it a step, and a model-invocable skill carries no note, so a hand-off from a skill Claude started on its own into a gated skill is still refused and goes back to the user. A probe on Claude Code 2.1.306 with Opus 5.5 and a two-skill gated plugin showed the difference — without the note the model called the Skill tool, was refused, and gave up; with it the model read the delegated file and completed the step, and a general-purpose subagent handed the path did the same. The note is placed by generation, not by per-site rules, so a delegation upstream adds needs no new rule, and a skill body that does not open with its title stops generation; `tests/validate.rb` asserts that every gated upstream-derived skill carries the note exactly once, directly under its title, and that model-invocable skills and the edition-owned `upgrade` skill do not. The workflows' `subagent-review` route reaches its gated skill this way too.

Ordinary workflow orchestration, which upstream added in v0.1.20, needs the same thing one level down. Its Coordinator hands steps to Executors and to an Evaluator, which run as subagents, and upstream leaves their model to harness defaults. Substitutions in `references/ordinary-agent-orchestration.md` have a Claude Code Coordinator dispatch them as Claude Code subagents that request `opus` unless the user names another model, and put the owning Aquarium skill's `SKILL.md` absolute path into each assignment for the subagent to read in full — however the hand-off is phrased, including Procedure node text such as `Use task-implement`, which is byte-canonical YAML that no rule may rewrite. The Evaluator receives the path of `goal-evaluator`'s `SKILL.md` and each Executor that of `references/executor-guidance.md`, and the retained v2 contract carries the same rule in its Primary, Worker, and Judge vocabulary. These rules repeat the note's reason — a subagent cannot load a gated skill through the Skill tool — so a rename of that tool retires both.

## How generation works

This repository is a **generated artifact** that packages the Aquarium development skills as a Claude Code plugin marketplace: the source of truth is the Codex plugin at [irootkernel/aquarium](https://github.com/irootkernel/aquarium), pinned here as a submodule and transformed by `scripts/sync.py`.

```
upstream/                        git submodule, pinned to one upstream commit
  plugins/aquarium/              the Codex plugin — never edited here
overrides/
  manifest.json                  path → SHA-256 of the upstream file each override was derived from
  codex-exemptions.json          path → SHA-256 of an upstream file whose remaining "Codex" mentions were reviewed
  skills/... references/...      full-file replacements for host-specific divergence
additions/
  agents/...                     host-only plugin subagents with no upstream counterpart
  skills/...                     edition-owned skill files, carried into the generated plugin
scripts/sync.py                  the transformation
plugins/aquarium/                generated output, committed
  agents/                        the bundled reviewer subagent
  hooks/                         the roadmap commit guard
  sync-manifest.json             upstream commit, overrides, exclusions, and per-file hashes
```

`sync.py` copies the upstream plugin's `skills/`, `references/`, `assets/`, `hooks/`, and `shared/`, drops the files and skills excluded by name, applies literal substitutions everywhere except the verbatim data directories, applies overrides, derives invocation gating from the upstream sidecars and drops them, opens every gated upstream-derived skill with the delegation note directly under its title, then adds the host-only files — the bundled reviewer subagent, the edition-owned `upgrade` skill, which must declare its own gating or generation refuses it, and the repository-state inspector `subagent-review` runs. It refuses to run against an empty submodule, refuses to run when upstream grows a plugin-root directory or file the transformation does not handle, fails if host-specific text survives, fails if a substitution rule matched nothing that ships, fails if a generated script cannot run, and refuses an addition under a skill the generated tree does not ship.

`shared/` arrived in v0.1.20: the adaptive-procedure helpers that every Podway-backed workflow and the repository inspector load from the plugin root. It carries no host text and is copied as is. The adaptive data beside it is stricter: `assets/adaptive/known-sources-v2.json` pins the SHA-256 of every bundled Podway Procedure, and the capability signatures and operation contracts pin canonical JSON of their node definitions, so a rewrite would break a digest nothing regenerates. `assets/adaptive/` and `assets/schemas/` are therefore `VERBATIM_DIRECTORIES`: every scan still reads them, but no rule may rewrite them, even by an accidental match, and the validator asserts them and `shared/` byte-identical to upstream. `shared/` also imports names from two generated scripts that script rules can rewrite — `skills/dev-setup/scripts/inspect_tools.py` and `goal-evaluator`'s `ordinary_assignment.py` — so the validator pins each imported name, because a renamed one would pass the parse and arity gates and break only at run time. The helpers need PyYAML and `jsonschema`, which upstream does not install either and global setup reports as a manual prerequisite; without them the selected-Procedure inspection fails closed with `missing-prerequisite` rather than guessing.

Upstream diagnoses Ouroboros by asking Codex — `ooo codex doctor` for its integration artifacts and `codex mcp get ouroboros --json` for its registration. Copied verbatim, neither component can ever report `configured` under Claude Code, and because the readiness rollup requires all four, Ouroboros would report `degraded` forever and every design skill would stay blocked. The generated inspector probes `claude mcp get plugin:ouroboros:ouroboros` instead: Ouroboros ships its Claude Code integration as a plugin, so a name that resolves proves the plugin is installed and enabled and therefore that the `/ouroboros:*` skills are reachable, while its `Status:` line carries the server's health. The skills do not need the server, so a resolved but unconnected entry degrades the registration and leaves the integration intact. The runtime component follows the same reasoning: upstream v0.1.13 runs `ooo mcp doctor --json` only when Codex directly launches the selected executable and accepts its isolated `uvx` launcher from the registration alone, and the plugin-scoped registration is exactly that isolated launcher's Claude analog, so the generated inspector derives `mcp_runtime` from it as `plugin_launcher_configured` and never runs the doctor, whose `mcp_import` check fails by design in the CLI's own MCP 1.x environment. Required-text assertions guard the block matches. v0.1.16 replaced upstream's stderr matching with a structured inventory — a failed `codex mcp get` now falls back to `codex mcp list --json`, and absence is proved only from that list — which restructured the failure branch of `classify_ouroboros_registration` around a `presence` key only upstream's probe sets. The generated inspector cannot use that inventory, because `claude mcp list` health-checks every approved server, so the whole function is now the anchor and the definite not-found is still read from stderr.

Skill discovery narrows for the same reason. Upstream resolves user-scoped skills from the Codex and shared cross-agent roots, and the first version of this fork merely added `~/.claude/skills` alongside them. That reported a skill installed only in another host's root as present here, where it cannot be invoked, and counted a cross-host copy of a skill as a duplicate installation — which upstream's provenance rules reject, so correctly installed paired skills came back degraded. The generated inspector now resolves the Claude Code roots alone, and `dev-setup` installs user-scoped skills into `~/.claude/skills`, because one host's artifact should diagnose one host.

An unmapped sigil is the quiet failure: it is valid Markdown naming a command the reader's host does not have, so neither a forbidden needle nor a required-text assertion notices it, and one needle per known sigil only ever catches the sigils that already exist. Generation therefore rejects any remaining lowercase `$name` in generated Markdown, which is what caught the five Ouroboros and Deslop sigils upstream introduced in v0.1.9. Uppercase spellings are environment variables the generated tree still needs and do not match.

Not every lowercase `$name` is a sigil, though, and v0.1.14 proved it: `task-commit` pins the commit identity through `git -c user.name="$aquarium_commit_name"`, a shell variable the scan read as an unmapped invocation. Dropping `_` from the pattern would close that case and silently admit any future `$snake_case` skill, so the exceptions are named instead. Each one must still occur in upstream Markdown, or generation stops and asks for it to be removed, and the two lists — one in `scripts/sync.py`, one in `tests/validate.rb` — are compared as sets like the forbidden needles.

A literal substitution rule fails just as quietly in the other direction. v0.1.10 dropped one Oxford comma from `Ouroboros package, Codex, and runtime components` and the rule stopped matching without a word, and three script rules died in the same release when upstream extracted a shared helper and added a parameter. Three script rules died again in v0.1.13, when upstream extracted the Ouroboros transport comparison into two launcher matchers and split the runtime component across the installed and not-installed paths, and were re-derived against the new anchors. Every rule must now rewrite text that ships: generation counts matches outside the override targets and fails naming any rule that matched nothing, so a dead rule is deleted or re-derived deliberately instead of rotting. The phrases that only ever occurred inside an override target were deleted for the same reason; the forbidden needles and the sigil scan still catch that text if an override is ever retired. Eight script rules died at once in v0.1.16: six because that probe-shape change reached every function that read the old probe, and two because upstream hard-coded the shared cross-agent skill root in `inspect_im_not_ai` and the trust table. The two Ouroboros registration rules became one whole-function rule and the rest were re-anchored. v0.1.17 killed five script rules and three Markdown rules: upstream moved the writing-skill root choice into two helpers, renamed the version constants and keyword the old replacements called, rewrote `inspect_im_not_ai` and the trust table around those helpers, dropped the Ouroboros upper bound, and rewrote the disposition and Ouroboros integration sentences the Markdown rules anchored on. The script rules were re-derived from the new functions rather than from the old replacements, the two helpers are deleted with their last callers, and the validator rejects any surviving reference to them. The v0.1.21 adoption, which absorbed four upstream releases, found twenty-two dead rules, twenty-one Markdown and one script, most of them killed by convergence rather than drift: fifteen were deleted — fourteen review-stack rules whose text upstream removed when its review converged on this edition's design, and the rule whose premise that Claude Code never reads `AGENTS.md` had become false — and six Markdown rules were re-derived against upstream's new ledger, bundle-handoff, registration, and goal text, together with the script rule for the global inspector's new signature. That one shows why a dead rule is re-derived against its live siblings rather than deleted: upstream appended a Sorage upgrade-preflight flag after the two per-home parameters this edition removes, and the call-site rule that drops their arguments stayed alive, so without the signature rule the flag would have bound to the first per-home parameter, passed the arity gate, and never reached the Sorage probe; a unit test now pins that binding.

A block substitution that drifts can also produce a script that parses but cannot run. ## Upgrade

```bash
git submodule update --init --recursive
git -C upstream fetch --tags origin
git -C upstream checkout <new-tag>
python3 scripts/sync.py
ruby tests/validate.rb
git add -A && git commit
```

Each override records the SHA-256 of the upstream file it came from. When upstream changes one of those files the sync stops and names it, because merging a stale override would ship guidance that no longer matches its source. Re-derive the override against the new upstream content and update `overrides/manifest.json`.

`/aquarium:upgrade` walks this sequence end to end — subagent-gathered delta analysis, approved re-derivations, validation, release, and the local installation refresh — behind explicit approvals at every mutating boundary.

## Validate

```bash
python3 scripts/sync.py --check
ruby tests/validate.rb
python3 -m unittest discover -s tests -p "test_*.py"
git diff --check
claude plugin validate --strict plugins/aquarium
```

`--check` regenerates into a temporary directory and fails if the committed output drifted. The Ruby validation covers only what this repository is responsible for — invocation gating against the upstream sidecars, the delegation note in every gated upstream-derived skill and nowhere else, host-neutral generated text, the commit hook's Claude Code contract, the bundled reviewer's frontmatter and the Subagent Review baseline it serves, byte-identical Podway Procedures and verbatim `shared/`, `assets/adaptive/`, and `assets/schemas/` trees, the names `shared/` imports from the generated scripts, manifest agreement, deliberate exclusions, compiled generated scripts, the README's override and Skills tables, every `/aquarium:` reference naming a shipped skill and every bare `aquarium:` one a shipped skill or agent outside upstream's named migration history, no skill directory shipping without its `SKILL.md`, and the marketplace shape. The forbidden-needle lists and the sigil exceptions are each compared as sets across `scripts/sync.py` and `tests/validate.rb`, because the guard is only as wide as its narrower half and an entry added to one side alone reports healthy. The 40 Python tests, discovered from every `tests/test_*.py`, execute the behaviour this repository authors in the shipped inspectors — the Claude Code MCP inspection, the skill roots, the writing-skill and Ouroboros probes, the global inspector and its Sorage preflight binding, the selected-Procedure prerequisite that fails closed without PyYAML and `jsonschema`, and the repository-state inspector, which must never run a Git filter the inspected repository or one of its submodules configures and must still see every mutation it compares. Upstream owns the prose contract and validates it in its own CI. The last command is Claude Code's own plugin validator and runs locally rather than in CI.

## Documentation style

Do not hard-wrap prose. Keep each prose paragraph on one source line; use line breaks only for structural Markdown, code, tables, lists, or other syntax where the break is meaningful.
